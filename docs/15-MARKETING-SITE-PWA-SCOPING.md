# 15 — Marketing Website + Progressive Web App: Scoping + Build Phases

**Status: scoped 2026-09-20, nothing in this document is built.** Same convention as `docs/11`, `docs/12`, and `docs/14`: fully scoped now, built in reviewable phases on explicit go-ahead. This document depends directly on `docs/12-LINKED-DEVICES-WEB-SCOPING.md` — the two are not independent efforts, and §3 below explains exactly why.

**The ask, restated precisely:** a modern, animated, fully-built marketing website (Netlify-hosted) with a homepage signup that reuses the app's own phone-OTP flow and funnels to a download page (native app links + PWA install, for both platforms), a "scan this QR code to use the desktop web version" feature, and a continuously-updated Progressive Web App that mirrors the full native app so anyone who installs it always has the latest shipped features.

## 1. The one finding that reshapes this whole document: the PWA is not a new build

`docs/12-LINKED-DEVICES-WEB-SCOPING.md` already investigated and confirmed, live, that **Expo Router's web export already works** for this codebase — `expo export --platform web` produces a real, running web build of the actual app, today. That means "mirror the full app as a PWA, kept in sync as the app is built" is not a second engineering effort to run in parallel with the mobile app forever — it is: take the web export that already exists, wrap it with a real PWA manifest + service worker, deploy it to Netlify, and put that deploy on autopilot in CI. Every feature the mobile app ships from that point on is _already_ in the PWA the next time it deploys, because it's the same source tree. The work in this document is packaging and deployment engineering, not a re-implementation of chat, wallets, or status.

The corollary is equally important: **the PWA inherits every native-vs-web gap `docs/12` already found and did not pretend away** — contacts sync, biometric app-lock, the camera/image picker, and native push notifications all need a real web behavior or an honest "not available here" degradation. This document does not re-litigate that list; it defers to `docs/12`'s own findings and treats "make the web build actually good enough to use" as a shared prerequisite for both documents, not a `docs/12`-only concern.

## 3. "Scan QR to use on PC" is `docs/12`, not a new feature

This is the single most important integration point in this document. WhatsApp's own "web.whatsapp.com" is exactly this pattern: a page that shows a QR code, paired by an already-authenticated phone, granting a **companion session** — never a primary login surface. `docs/12` already designed the pairing protocol, the reduced-privilege session model ("chat-and-status only — no top-up, no withdrawal, no bank-account changes, no credit transfers from a non-primary session, at least for v1"), and the security posture for exactly this. This document's job is narrow: **host the page that shows the QR code**, on the marketing site's `/web` route, and hand off to `docs/12`'s own pairing flow for everything after the phone scans it. No pairing logic, session model, or privilege-scoping decision gets re-designed here — building this page before `docs/12` is built is not possible, and that dependency should be explicit rather than glossed over.

## 4. Homepage signup — OTP verification, not web login

The homepage embeds the **existing phone-number + OTP screen** (the same Edge Function-backed flow the mobile app already uses to create an account) as a web component, not a re-implementation:

1. Visitor enters a phone number on the homepage.
2. Same OTP send/verify Edge Functions the mobile app calls today (`docs/05-API-REALTIME-SPEC.md`'s existing contract) — **the marketing site has no auth logic of its own**, it is a second, unauthenticated caller of an already-built API, exactly the way `CLAUDE.md`'s "no financial/trusted logic on the client" principle generalizes to any new client this project adds.
3. On successful verification, the visitor is **not** logged into a web session with app access — they land on the Download page (§5) with their number already confirmed. This matches the ask precisely ("once code is sent to the user and the enter to verify, it lands them on download the app to login") and matches the security posture recommended in §3: **no path exists for a brand-new account to become fully active without going through the real app or the real PWA** — the marketing site's job is lead capture and OTP pre-verification, never full onboarding.
4. **New risk this introduces, flagged directly**: the mobile app's OTP-send endpoint has only ever been called from inside an installed app, behind whatever basic bot-resistance an app store install implies. A public, unauthenticated website form calling the same endpoint is a materially more attractive target for automated abuse (OTP-bombing a phone number, scraping the endpoint for enumeration). **Recommendation: add a CAPTCHA/bot-check (Cloudflare Turnstile or equivalent) in front of the web-facing OTP-send call specifically**, without changing the endpoint's contract for the mobile app's own calls to it — a new guard at the new entry point, not a change to the existing one.

## 5. Download page and the store-badge bootstrapping problem

Four install paths, matching the ask exactly: Android (Play Store), iOS (App Store), PWA for iOS (Safari "Add to Home Screen" walkthrough — iOS doesn't support a native install prompt the way Chrome/Android does, so this needs real, illustrated instructions, not just a button), PWA for Android (a real `beforeinstallprompt`-driven install button, which Chrome on Android supports natively). **Honest bootstrapping note**: real store badges require the app to actually be listed, which per `docs/08-BUILD-PHASES-ROADMAP.md` is Phase 7, not yet reached. Until then, this page should show real, honest interim state (TestFlight / Play internal testing links, or a clearly-labeled "coming soon") rather than placeholder badges that link nowhere — a small thing, but a marketing site that visibly lies about availability is a worse first impression than an honest waitlist.

## 6. Shared legal content — reuse, don't fork

The mobile app already has real Terms of Service / Privacy Policy content (`apps/mobile/content/legal/`, rendered at `/legal/terms` and `/legal/privacy` per `settings/help.tsx`). The marketing site's own legal pages must render **the same source**, not a second hand-maintained copy — concretely, promote that content into a shared package (e.g. `packages/legal-content/`) that both the mobile app and the new marketing site import, so a ToS update (frequent, given `docs/07-COMPLIANCE-LEGAL.md`'s own still-open legal-review checklist) is one edit, not two, and the two surfaces can never silently drift out of sync — exactly the "adopt what's already built rather than rebuild it" instruction this whole request was framed around.

## 7. Technology choice and hosting

- **Marketing site**: a separate, lightweight static/SSG app — **Next.js or Astro**, not the Expo/React Native stack. Reasoning: this is a content-and-SEO-driven public site (organic search and app-store-adjacent discoverability genuinely matter for user acquisition), and a server-rendered/statically-generated site is the correct tool for that job — a client-side-only SPA (or shipping the Expo web bundle as the marketing site) would hurt SEO and first-paint time for no benefit, since none of the marketing pages need the mobile app's own component tree. Animation via Framer Motion (or the chosen framework's standard equivalent) for the "clean transitions, smooth hovers" ask — a normal, well-supported choice, no bespoke animation engine needed.
- **PWA**: the existing Expo Router web export (§1), with a real `manifest.json`, a service worker (installable, offline app-shell, versioned cache-busting on deploy), and platform-specific install UX per §5.
- **Hosting — two separate Netlify sites**, not one: `involveme.com` (marketing, its own build pipeline) and `app.involveme.com` (the PWA, Expo's own web build pipeline) — mirrors how WhatsApp itself separates `whatsapp.com` from `web.whatsapp.com`, and means a marketing-site deploy can never break the PWA and vice versa. Netlify handles SSL/DNS for both with no custom work needed.
- **CI**: the PWA's Netlify deploy is triggered on every merge to `main` that touches the mobile app (or the shared web-relevant packages) — this is the literal mechanism behind "a user who downloads the PWA at any time has the latest features," not a manual or occasional re-publish step.

## 8. Gaps investigated and recommendations

- **Web Push is a different mechanism from Expo's native push**, already noted as a `docs/12` finding — the PWA needs its own Web Push integration (a real, separate build item) or should honestly show notifications as unavailable until that's built, never silently fail.
- **Service worker vs. the app's own offline strategy (`docs/13-OFFLINE-MODE-SCOPING.md`)**: the PWA's service worker should cache the app shell/static assets only, and defer all data-freshness/outbox behavior to the exact same TanStack-Query-persisted-cache + outbox mechanism `docs/13` already designed for the native app — one offline strategy, reused, not two competing caching layers that can disagree with each other about what "up to date" means.
- **Privacy-respecting analytics**: given `docs/07-COMPLIANCE-LEGAL.md`'s already-cautious NDPA/data-protection posture, recommend a privacy-first analytics tool (Plausible/Fathom-class — no cross-site tracking, no cookie banner needed) over invasive tracking, consistent with how the rest of this product already treats user data.
- **The OTP-abuse risk in §4** is the single highest-priority security gap this document surfaces — it must be closed in the same phase the homepage signup ships, not after.
- **PWA session model**: per §3, the PWA is a _linked-device_ client requiring an already-authenticated phone to pair via QR — not an independent primary-signup surface. This is called out explicitly as the recommended design (matching WhatsApp's own model and `docs/12`'s reduced-privilege session scoping) rather than left ambiguous; an alternative "let people sign up and log in entirely from the browser, no phone required" design was considered and is **not** recommended, since it would open a second, independent authentication surface for a product that custodies real money — exactly the kind of new attack surface `docs/06`/`docs/07` already treat carefully everywhere else in this codebase.

## 9. Build phases (for your review — nothing starts until you say go on a specific phase)

**Phase A — Marketing site core**
Home, How it works, Pricing, Security & Trust, About, Contact — static content, animation/design pass, deployed to `involveme.com` on Netlify. No signup, no PWA yet. Exit criteria: a real, complete, animated public site exists and is live.

**Phase B — Shared legal content + ToS/Privacy pages**
§6 — promote legal content into a shared package, wire both apps to it. Small, independent, safe to do any time after Phase A.

**Phase C — Homepage signup (OTP) + Download page**
§4 + §5, including the bot-abuse guard (non-negotiable, ships in the same phase, not after). Store badges start in "coming soon"/TestFlight-honest mode per §5 until Phase 7 of the main roadmap lands.

**Phase D — PWA packaging**
§1/§7 — manifest, service worker, install prompts for both platforms, deployed to `app.involveme.com`, CI auto-deploy wired up. **Depends on `docs/12`'s "make the web build actually usable" work being done first** — this phase is where that dependency becomes concrete and blocking, not optional.

**Phase E — QR/desktop web entry point**
§3 — the marketing site's `/web` page. **Fully dependent on `docs/12`'s pairing flow being built** — this phase cannot start before `docs/12`'s own phases are further along than they are today; listing it here keeps it visible and reviewable rather than silently deferred.

**Phase F — Web Push + offline polish**
§8's remaining items, once the higher-priority phases are live.

Suggested order: A → B → C → D, with E specifically gated on `docs/12`'s own progress (it can run whenever that dependency clears, not necessarily last) and F picked up opportunistically. A and B can start immediately and touch nothing financial or identity-related; C is the first phase that needs the bot-abuse review before shipping; D and E are the two phases that turn "marketing site" into the literal product surfaces the ask described.
