## 1. Economics — why this can't reuse §4/§5's message-billing shape

Message billing works because a message is a single, instantaneous, already-fully-known-cost event: compute `credits_charged` once, debit once, done. A call is none of those things — it's an open-ended duration nobody knows in advance, which breaks the "compute cost, then charge" pattern at its root.

**The core design question: pre-authorization + running debit, not compute-then-charge.**

```
call_connect_fee_credits     = flat per-call connection cost (config), analogous to
                                message_base_credits — charged once, on answer, not on ring
call_per_minute_credits      = per-minute rate (config) — LiveKit itself bills voice and
                                video at the same per-participant-minute rate (§1 below),
                                so a voice/video price gap, if any, is a product choice
                                about UI/bandwidth scope, not a pass-through provider cost
```

- On answer (not on dial — a call nobody picks up shouldn't cost anything, same "B never had a claim on credit they didn't respond to" principle §5 already establishes for unanswered messages), debit `call_connect_fee_credits` and start a running per-minute meter.
- The meter needs a **live low-balance cutoff**, not a post-hoc bill — unlike a message, a call can't be "rejected for insufficient credit" after the fact once the parties are already mid-conversation. This means either: (a) a background job ticking every N seconds during an active call, debiting and hanging up on insufficient credit, or (b) a client-side warning + grace period backed by a server-side reconciliation that force-ends the call and settles for actual elapsed time if the client's own end-signal never arrives (calls can end by app crash, connection loss, force-quit — none of which guarantee a clean "call ended" signal reaches the server). **(b) is very likely the right shape** — a server that can't trust the client to say "I hung up" needs its own authoritative timeout regardless, and reusing that same mechanism for "ran out of credit" avoids building two parallel truncation paths.
- **Billing granularity**: per-minute vs. per-second matters a lot more here than message word-blocks did, because rounding a 90-second call up to 2 minutes is a much bigger relative overcharge than rounding a slightly-long message up to the next word block. Recommend per-second accrual with a per-minute _rate_ (i.e. `credits = ceil(seconds_elapsed / 60 * per_minute_rate)` — billed in fractional-minute credit amounts, not truncated to whole minutes), same "don't let rounding be a silent revenue leak or a silent overcharge" principle §3's `leftover_kobo` handling already establishes.
- **Who earns**: same A-pays/B-earns split as 1:1 messaging (§2), with the same 20% `platform_earning_take_bps` cut on B's side — no reason to invent a second take-rate unless a real cost-modeling pass (§2 below) says otherwise. Unlike escrow, this settles as it accrues (or in short periodic batches), not on "B replies," since there's no equivalent trigger — the whole call _is_ the two-way exchange.
- **A call that never connects** (no answer, declined, one side's device fails to establish media) charges nothing — same principle as an unanswered message's escrow refund.
- **A call that drops mid-stream** (network loss, app killed) settles for actual elapsed time up to the last point the server can attest to (last successful meter tick), not the full intended duration and not zero — refunding an entire connected call because the last few seconds didn't get billed would be a bigger and easier exploit than the rounding question above (repeatedly "network drop" a call right after connecting).

**Cost-modeling question — now answerable with real LiveKit numbers (session 21), not fully resolved to a config default:** LiveKit bills **WebRTC participant-minutes**, not call-minutes — a 2-person voice or video call burns **2 participant-minutes per wall-clock minute** (each connected SDK client counts separately), a detail that must be built into the metering math, not just the pricing table. Real current rates (`livekit.com/pricing`, confirmed live 2026-09-18, not assumed from training data — same "verify live, don't guess" discipline session 17's real Flutterwave capability check used, `docs/03-ECONOMY-LEDGER.md` §12):

- **Free tier ("Build")**: 5,000 WebRTC participant-minutes/month, no card required, **hard stop** on exceeding any quota mid-month (new requests fail outright — no overage billing, no grace period). Enough for real internal testing and a small closed beta, not enough to launch on.
- **Ship tier ($50/mo)**: 150,000 participant-minutes included, then **$0.0005/participant-minute**. No separate audio-vs-video rate — same meter for both, so video's higher bandwidth cost to LiveKit is already priced in equally with audio at this layer (it isn't cost-free to skip video, LiveKit just doesn't itemize it separately).
- **Scale tier ($500/mo)**: 1.5M participant-minutes included, then $0.0004/participant-minute; also the minimum tier for regional data residency and HIPAA/BAA — relevant to §6's compliance note below, not to margin math directly.

**What this means for `call_per_minute_credits`:** the provider's marginal cost per **call**-minute (not participant-minute) for a 1:1 call is **2×** the per-participant rate above — e.g. at Ship-tier overage pricing, $0.0005 × 2 = $0.001 per call-minute before InvolveMe's own take. `call_per_minute_credits`'s cash value (via `pricing_config`'s credit-to-₦ rate) must clear that floor with real margin left over, the same way the 2% top-up fee was checked against Flutterwave's own cost in §3 — this is a concrete number to run through that same check before setting a default, not a values judgment to make blind. Still not fully resolved here: the actual `pricing_config` value, which is a product/margin decision for whoever schedules the real build, informed by this floor rather than replacing it.

## 2. Calling infrastructure — provider evaluation

Real-time audio/video needs a signaling layer (who's calling whom, session negotiation) plus a media layer (the actual audio/video transport — raw peer-to-peer WebRTC struggles at scale with NAT traversal and needs TURN relay infrastructure neither Supabase nor this app currently operates). Candidates considered, roughly in "less own-infra" to "more own-infra" order (kept for the historical record — §2b below is the actual decision):

| Option                                                                                                                                                         | What it gives you                                                                        | What it costs                                                                                                                                                                                                                                            | Fit                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Managed WebRTC platform** (e.g. a provider offering an SDK + per-minute billing, category examples: Agora, Twilio Video, Daily, Stream Video, LiveKit Cloud) | SDK handles signaling + TURN + media relay; React Native SDKs exist for all of the above | Real, metered, provider-specific per-minute pricing — this is the number §1's cost-modeling question needs                                                                                                                                               | Fastest to ship, least "stay lite" (a real new SDK dependency, likely the single largest native dependency this app has added)                                           |
| **Self-hosted LiveKit/Janus/mediasoup**                                                                                                                        | No per-minute provider fee                                                               | Real infrastructure to run, patch, and scale (a media server is a genuinely different operational category from this app's current all-Supabase footprint) — a bad fit for a team currently running zero own infrastructure                              | Only worth it at a scale where provider per-minute fees would clearly cost more than running servers                                                                     |
| **Raw WebRTC, peer-to-peer, Supabase Realtime as the signaling channel**                                                                                       | Zero new infra for signaling (Realtime already exists here)                              | No TURN relay of your own means calls between two users on restrictive NATs (common on mobile carrier networks) will frequently fail to connect at all — this is the option most likely to produce "calls just don't work sometimes" as a support burden | Cheapest to prototype, weakest reliability; realistically needs a TURN service (many managed WebRTC platforms include one, which pulls back toward the first row anyway) |

**Original recommendation (superseded by §2b's actual decision):** start with a managed provider for the MVP (first row) — this app has zero real-time-media operational experience, and "does the call reliably connect across real mobile networks" is a solved problem in that tier and a genuinely hard one to solve from scratch. Revisit self-hosting only if provider per-minute costs become a real margin problem at scale, the same "not now, revisit if it becomes real" posture `docs/06-SECURITY-FRAUD-LOOPHOLES.md` already uses for a couple of its own deferred items.

**Signaling for an incoming call while the app is backgrounded/killed** needs a real push notification (Expo push, already wired up per `lib/push.ts`) that triggers native call UI — see §5.

## 2b. Why LiveKit, and what "build with self-host migration in mind" actually means

**Decision, 2026-09-18:** LiveKit, starting on LiveKit Cloud's free tier. Real facts confirmed live against LiveKit's own docs/pricing/GitHub (2026-09-18), not assumed from training data:

- **Free tier ("Build"), $0/mo, no credit card required**: 5,000 WebRTC participant-minutes/month, 1,000 recording minutes, 1,000 SIP minutes, 100,000 observability log entries. Exceeding any quota mid-month is a **hard stop** (new requests fail; no surprise overage bill) — safe to develop against without a runaway-cost risk, but not a launch-scale allowance (see §1's math: 5,000 participant-minutes is 2,500 minutes of 1:1 call time total, across every user, per month).
- **Self-hosted LiveKit OSS is genuinely Apache-2.0** (no BUSL/source-available catch to watch for) — `github.com/livekit/livekit`, official Docker images and Helm charts exist, and a single-node deployment needs **no Redis and no separate TURN server** (LiveKit embeds its own TURN). Redis only becomes mandatory for multi-node/distributed clustering (shared room state) — a single-node self-host is realistically a weekend-scale infra task; multi-node HA is a real, ongoing ops commitment this app has no experience with yet, matching this doc's own "revisit self-hosting only if it becomes a real margin problem" posture, just with a much lower bar to actually do it than the original self-hosted-Janus/mediasoup row implied.
- **The migration path is genuinely low-risk, which is the actual reason LiveKit was chosen over the other managed options**: Cloud and self-hosted LiveKit run the **same open-source server**, the **same client SDKs**, and the **same JWT-based token format** — moving from Cloud to self-host is a `LIVEKIT_URL`/key/secret swap at the Edge Function config layer (§2c), not a client rewrite or a new integration. This is structurally different from, say, an Agora→self-host migration, which would mean replacing the SDK and the whole calling integration. **One thing this doesn't carry over automatically**: Cloud-only features — regional data residency and HIPAA/BAA (both gated to the $500/mo Scale tier), and Cloud's managed recording/egress/SIP infrastructure — have no self-hosted equivalent without standing up that infrastructure yourself. None of those are in this app's MVP scope (§7), so this isn't a blocker, just a thing to re-check if the MVP scope grows before the self-host migration happens.
- **Practical implication for how this gets built**: don't hardcode `wss://involveme-l9ghhp4h.livekit.cloud` anywhere — every call site reads `LIVEKIT_URL` from config (already true by construction, since it's a Supabase secret, never a literal), so flipping to a self-hosted URL later touches one Edge Function secret, not application code.

## 2c. Credentials and secret handling

Real LiveKit Cloud free-tier credentials exist for this project as of session 21 and are stored as **Supabase Edge Function secrets** — `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` — the same mechanism and same `_shared/*-config.ts` loader pattern `supabase/functions/_shared/flutterwave-config.ts` already establishes for Flutterwave's credentials. **The API key/secret pair must never reach the mobile client or the repo** — it signs room-access JWTs server-side only (§3's token-minting design); the mobile app only ever receives a short-lived, per-room token from an Edge Function call, the same posture every other credential in this codebase already follows (CLAUDE.md's "no financial logic on client" extends naturally to "no calling credentials on client" — a leaked LiveKit API secret would let anyone mint a token to join or eavesdrop on any room). `LIVEKIT_URL` itself is not sensitive (it's a public WebSocket endpoint, same category as `EXPO_PUBLIC_SUPABASE_URL`) but was kept as an Edge-Function-only secret rather than an `EXPO_PUBLIC_*` build-time var so a Cloud→self-host URL change never requires a mobile rebuild/OTA, just a secret update.

## 3. Data model sketch (not built — shape only, for the eventual migration)

New tables, parallel to `group_threads`/`group_messages` rather than extending `threads`/`messages` (same "don't fork the tested 1:1 money path with `if is_call` branches" reasoning `docs/02-DATA-MODEL.md`'s group-threads note already gives):

- `calls`: `id, thread_id, caller_id, callee_id, kind ('voice'|'video'), status ('ringing'|'connected'|'ended'|'missed'|'declined'|'failed'), livekit_room_name, started_at, connected_at, ended_at, billed_seconds, credits_charged, payer_earning_credits, platform_take_credits`. `livekit_room_name` should be a server-generated opaque value (e.g. the call's own `id`), never derived from anything a client could predict or reuse — LiveKit rooms are join-by-name, so an enumerable/guessable name would let an unrelated party mint their own token for someone else's room name and attempt to join (§4's fraud posture already treats colluding-parties abuse as a first-class concern; an _unrelated_-party join is a different, worse bug class to rule out by construction, not by review).
- A periodic-billing mechanism needs its own audit trail distinct from a single ledger entry per call — likely `call_billing_ticks (call_id, tick_at, seconds_billed, credits_charged)` so a disputed call has a real accrual history, not just a final total. Exact shape is a real design question for whoever picks this up, not settled here.
- `pricing_config` keys: `call_connect_fee_credits`, `call_voice_per_minute_credits`, `call_video_per_minute_credits` (video plausibly priced higher — costs the provider more, per §1/§2), `call_platform_take_bps` (independently tunable from `platform_earning_take_bps`, same "each take-rate gets its own key" rule CLAUDE.md rule #9 and every existing take-rate in this codebase already follow), `call_low_balance_grace_seconds` (how long a call survives after the payer's balance can no longer cover the next tick, before a forced hang-up).
- **Token-minting Edge Function** (new, e.g. `create-call-token`): the one new server-side surface LiveKit itself requires. Mints a short-TTL room-join JWT via `livekit-server-sdk` — confirmed (session 21 research) that this package's v2 runs natively on Deno, not just Node, so it's a normal Supabase Edge Function with no extra runtime needed. Must check the caller has a live thread with the callee (same RLS-equivalent check every other Edge Function already does) and a non-zero balance _before_ minting a token, matching CLAUDE.md rule #1 — the token itself is the only thing that touches `LIVEKIT_API_SECRET` (§2c), and it must carry only the specific `roomJoin`/`identity` grant for that one call, not a general-purpose credential.

## 4. Fraud/abuse surface — likely worse than group chat's, not better

§10's group-chat exploit (colluding accounts converting `topup_credit` into cash with no reply-gate) has a direct, arguably easier analog here: two colluding accounts call each other and leave the call connected, silent, for hours. Unlike a scripted message flood, this needs **no scripting at all** — just two phones left face-down — and produces a steady, automatic credit-to-cash conversion for as long as the call stays up. This is not a hypothetical to defer past Phase 5 the way group chat was; if calls ship pay-per-minute, this needs its own answer before launch, not after:

- A **maximum single-call duration** (config, not hardcoded) is close to mandatory, not optional the way it was debatable for group chat.
- The existing collusion-detection infra (`fn_run_collusion_detection`, `docs/06-SECURITY-FRAUD-LOOPHOLES.md` §2) was built against message/thread patterns — confirm it actually fires on a call-heavy account pair, don't assume it generalizes for free.
- Velocity limits (§6's existing infra) likely need a calls-specific variant — "N minutes of calls per day" is a different shape than "N messages per day."
- KYC-tier gating on _earning_ from calls (not just withdrawing) is worth considering given how passive the exploit is — a real product/risk decision for whoever scopes the actual build, flagged here rather than answered.

## 5. Mobile — what "active" call buttons actually require

The punch-list ask was "add the Video and Audio call buttons to the header... that should be active too." Concretely, "active" means all of the following, not just a button that does something:

- **LiveKit's React Native SDK is not Expo-Go-compatible** (confirmed, session 21 research) — `@livekit/react-native` bundles native code (`@livekit/react-native-webrtc`), so this feature genuinely requires an `expo-dev-client` custom build via EAS, plus `@livekit/react-native-expo-plugin` wired into `app.json`/`app.config.js`. This isn't new for this app (Batches C1/E1/F already queued native modules behind a held `eas build`), but it does mean calls **cannot** ship as a JS-only OTA update the way this session's other work did — the held-build queue and calls should be planned as one deliberate build, not squeezed into a future OTA-only session.
- **Permissions**: microphone (voice + video) and camera (video) — new `expo-camera`/provider-SDK-specific permission prompts, each needing the same `withAppLockSuppressed` bracket this session's app-lock fix established for every other system dialog (see `lib/appLock.ts`'s header comment) — a call built without that bracket would immediately reproduce the exact false-positive-relock bug this session just closed.
- **Ringing UI** for the callee, including **while the app is backgrounded or killed** — this is what CallKit (iOS) / ConnectionService (Android) exist for: OS-level native call UI that can wake and ring even when the app process isn't running, the same way a real phone call or a WhatsApp call does. Skipping this and only ringing while the app happens to be foregrounded would feel broken compared to every reference app this feature is being built to match.
- **In-call UI**: mute, speaker/earpiece toggle, camera flip + on/off (video), end-call, an elapsed-time/cost indicator (this app's whole identity is pay-per-X — hiding the running cost during a metered call would be a bad-faith UX choice, not just an omission).
- **Low-balance handling**: a warning before the grace-period cutoff (§3's `call_low_balance_grace_seconds`), not just a call that silently drops.
- **Call history**: the `calls.tsx` tab stops being a stub and becomes a real log (missed/answered/duration/cost), reusing the transaction-history patterns `TransactionHistory`/`useLedgerEntries` already established for wallet activity.

None of this is buildable as a quick addition to the existing header — it's the reason this whole feature needs its own milestone plan rather than a spot in a bug-fix session.

## 6. Compliance — a second look needed, not assumed clear

`docs/07-COMPLIANCE-LEGAL.md`'s money-transmission framing was written against message-based credit flow; pay-per-minute calling is the same underlying wallet mechanism (no new transmission concept) but real-time audio/video adds surface that document doesn't currently cover at all:

- **Call-recording consent law** varies by jurisdiction (many require **all**-party consent, not just one-party) — only relevant if this app ever records or stores call audio/video. If it never does (recommended default — "stay lite," and recording adds a whole storage/retention/subpoena-exposure problem this app doesn't need), this becomes a one-line "we don't record calls" statement rather than a real compliance project. Decide "never record" explicitly, in writing, before building rather than defaulting into it by omission. LiveKit Cloud's recording/egress feature (§2b) should stay unused for this reason — its existence doesn't change the recommendation.
- **Data residency, now a concrete finding, not a generality (session 21):** LiveKit's regional data-residency pinning is a **Scale-tier-minimum feature ($500/mo)** — on the free/Ship tiers this app would actually launch on, call media routing is not region-pinned. `docs/07-COMPLIANCE-LEGAL.md` §5's NDPA framing (built around phone numbers/BVN/message content sitting in Supabase, a known-region Postgres instance) has never had to consider "which country does a real-time media packet transit through" before — worth a real answer (does NDPA reach transient, unrecorded media transit the way it reaches stored data? genuinely unclear, flagged for counsel, not answered here) before this ships in a jurisdiction as strict as Nigeria's, not after.
- Real-time media makes this app's data-protection posture (what crosses the wire, through which provider, in which jurisdiction) worth a fresh look beyond the residency point above, same "add this section to the pre-launch checklist when the feature is actually scheduled" instruction §10 gives itself for group chat's own compliance angle.

## 7. Suggested MVP scope, if/when this is picked up

Not a commitment, a starting recommendation for whoever scopes the real build:

- **Voice only first, video second** — video adds real UI surface (camera flip, video permission, larger bandwidth per call, per §5) for a feature that's unproven at any volume yet, even though LiveKit's own per-minute _billing_ doesn't itemize video higher than audio (§1, corrected from this doc's original assumption — confirmed session 21, one shared WebRTC-minute meter for both). The cost case for voice-first is UI/bandwidth scope, not a provider-pricing difference; voice alone already exercises every hard part (metered billing, ringing/CallKit, fraud gating).
- **1:1 only, no group calls** — a group call's billing model (who pays, does everyone pay, does only the initiator pay) is its own unanswered design question layered on top of an already-new metered-billing model; don't stack two unresolved designs in one build. (LiveKit itself supports multi-party rooms natively whenever this is picked up — not a provider limitation, a deliberate scope cut on this app's side.)
- **The free-tier ceiling (§2b: 5,000 participant-minutes/month) is fine for build-and-internal-test, not for even a small real launch** — 2,500 minutes of total 1:1 call time across every user, per month, is exhausted fast. Budget for the $50/mo Ship tier by the time this reaches a closed beta with real users, not at the point it's already been exceeded (a "hard stop," not an overage bill, per §2b — a free-tier ceiling hit reads to real users as calling being broken).
- **A provider cost-model pass against the real `pricing_config` credit rate (§1) happens before any code**, same "plan the doc, then build to it" convention this session's group-chat work followed for its own migration — §1 now has the real per-participant-minute floor to run that check against.

## 8. Where to begin, when this is actually picked up

Not started this session — a concrete first milestone for whoever picks this up next, ordered so each step produces something independently verifiable before the next one depends on it:

1. **Prove the LiveKit round-trip in isolation, before touching this app's real UI or billing.** A throwaway two-device (or two-browser-tab) test: the `create-call-token` Edge Function (§3) mints a token against the real free-tier project, two clients join the same `livekit_room_name` and actually exchange audio. This validates the token-minting shape and the Deno-compatible server SDK claim (§2b) against real infrastructure before any app code depends on it.
2. **Run §1's real cost-model pass** — take the per-participant-minute floor now documented there and the actual `pricing_config` credit-to-₦ rate, and set a real `call_voice_per_minute_credits` default with margin confirmed, not assumed. This blocks the billing migration below, so do it early.
3. **Migration**: `pricing_config` keys + the `calls`/`call_billing_ticks` tables (§3), `create-call-token` Edge Function, and the metering/settlement functions (§1's pre-auth + running-debit design) — built and dev-DB-verified the same way every prior wallet-touching migration in this repo has been (ledger-conservation + concurrency tests, per this repo's own CLAUDE.md testing rule).
4. **Mobile, gated on an explicit `eas build` go-ahead** (§5) — `@livekit/react-native` + the Expo config plugin, wired into a bare voice-only call screen (no CallKit/ConnectionService yet) against the migration above, proving end-to-end billing with a real device build before investing in native ringing UI.
5. **CallKit/ConnectionService + call history UI** (§5) once step 4's core loop is proven — this is genuinely the largest remaining UI lift and shouldn't gate proving the billing model works first.
6. **§4's fraud answer (max call duration, collusion-detection generalization) ships in the same milestone as step 3, not after** — per §4, this is "needs its own answer before launch," not a follow-up.

Steps 1-2 are cheap (hours, not days) and de-risk everything after — a reasonable place to actually start once given the go-ahead, without committing to the full multi-week build yet.

## Non-goals for any v1 of this feature (explicit, not just unlisted)

Call recording/transcription, group calls, screen sharing, call-quality analytics/telemetry beyond what the chosen provider gives for free, any free tier or promotional free-minutes mechanic (a referral/promo-adjacent decision `docs/06` §10 already flags as needing its own prerequisites this app doesn't have yet). LiveKit's own cloud agents/telephony(SIP)/noise-cancellation features (available on the plans researched in §2b) are also explicitly out of scope — this app needs 1:1 voice/video calling, not LiveKit's full product surface.
