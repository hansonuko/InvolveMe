# 14 — Admin Dashboard: Scoping + Build Phases

**Status: scoped 2026-09-20; Phases A–F built and merged, and both trimmed items from Phase D's scope (§4.2's Service Pricing toggle, §4.3's pricing-strategy-switch framework) now built too, as of 2026-09-24** (see `docs/00-SESSION-HANDOFF.md` for the per-phase build record). Phase G (§8 polish) is in progress: piece 1 (user location stats) and piece 2 (admins list/management page — a real gap found separately from §8's own list, not one of its named items) are both built and merged. Piece 3 (CSV export) is the only remaining open piece of this entire document, and it remains explicitly low-priority. Built one phase/piece at a time, on the user's own explicit go-ahead per piece, same discipline `docs/11`/`docs/12` already established for calls and linked devices. This closed a gap `docs/08-BUILD-PHASES-ROADMAP.md` Phase 5 already flagged and left open — "no dedicated [admin/review-queue] tooling exists or is planned... the actual answer, confirmed this session, is Supabase Studio directly" — that was a reasonable placeholder at zero users; it stopped being one the moment there was a real fraud queue, a real pricing lever, and a real treasury to manage.

**The ask, restated precisely:** a fully-featured, modern, responsive, role-based admin dashboard — a genuine internal ops console in the shape Meta/WhatsApp-scale and comparable fintech platforms actually run internally (Stripe's own Dashboard, a bank's ops console — not literally WhatsApp's consumer UI, which has no public admin surface to model). Full wallet/treasury visibility and control, a super-admin layer that can adjust roles, pricing, and which services charge at all, a reports/fraud review queue, user analytics by location, and a search-everything experience — built for real traffic, not a weekend Retool script.

## 1. The most important finding before any design decision: this is a _second privileged surface_ over money the app already treats as its highest-stakes concern

Every rule in `CLAUDE.md` about money — no client-side financial logic, `SECURITY DEFINER`-only writes, append-only ledger, explicit per-function grant locking (rule #11) — exists because a client holding nothing but an anon key must never be trusted with a balance. An admin dashboard is a **second, far more powerful** client: one that legitimately needs to adjust balances, freeze wallets, change pricing, and eventually move the platform's own money. It inherits every one of those rules and adds a new one on top: **the admin backend is the only client in this system ever authorized to act as a human with elevated trust, and every one of its writes must be individually attributable, logged, and — for the highest-risk actions — dual-approved.** Get this document's §7 (security architecture) wrong and it becomes the single largest attack surface in the whole product, worse than anything a consumer-facing bug could do, because it starts with the keys to the vault.

## 2. Real gaps found investigating the current codebase (not assumed — checked against the actual schema/functions)

- **No admin authentication or authorization exists anywhere.** The literal current "admin dashboard" is direct Supabase Studio access with the project's own service-role credentials — fine at zero users, a genuine liability at any real scale (no per-person audit trail, no role separation, no way to revoke one person's access without rotating the key for everyone).
- **No RBAC schema exists.** Nothing in `docs/02-DATA-MODEL.md` models "an admin" as a first-class concept at all.
- **Correction (2026-09-20, pre-Phase-A review): `pricing_config_history` does exist** — this bullet's original claim was wrong, caught re-checking migrations directly rather than trusting the earlier pass. `20260912070729_create_core_schema.sql` creates the table and a `before update on pricing_config` trigger (`record_pricing_config_change`) that inserts one row per change automatically; `20260917130000_multicurrency_schema.sql` extends it with a `currency` column. So every `pricing_config` write, including today's raw Studio edits, is already captured with `old_value`/`new_value`. **The real, narrower gap:** the trigger hardcodes `changed_by = 'system'` with no way for a caller to attribute a real actor — so the audit trail exists but is anonymous. §4.2's actual job for Phase D is making the admin pricing-update path pass through a real admin identity (e.g. via a session-scoped Postgres setting the trigger reads, or by having the admin update function insert its own history row with the real `changed_by` before/instead of relying on the trigger), not building the table from scratch as originally stated.
- **The platform has been accumulating its own revenue since day one with no way to actually get it out.** `fn_credit_platform_revenue` (`docs/02-DATA-MODEL.md` §5) has been crediting `platform_revenue_topup_fees`/`platform_revenue_earnings_cut` correctly since session 14 — but `fn_initiate_withdrawal`/`withdraw` are scoped entirely to _user_ wallets (`withdrawable_cash`). **There is no function, Edge Function, or process anywhere in this codebase that pays InvolveMe's own accumulated revenue out to InvolveMe's own bank account.** This is the real substance behind the "restore all monetary transactions... with full withdrawable capabilities" ask: nothing needs to be _restored_ — the ledger is append-only and has the complete, correct history since the first transaction ever recorded (that's the entire point of `CLAUDE.md` rule #4) — but a real **platform treasury withdrawal path has never existed and must be built.** §5 below is the design for it.
- **The fraud/reports review queues genuinely have zero UI.** `fraud_signals` (`docs/06-SECURITY-FRAUD-LOOPHOLES.md` §2) and `user_reports` (`docs/02-DATA-MODEL.md`) are both real, populated tables with **no `SELECT` grant to any client role at all** — by design, but that design assumed Studio access as the reviewing mechanism. This dashboard is what actually closes that gap.
- **The "second admin sign-off" rule for `manual_adjustment` ledger entries (`docs/02-DATA-MODEL.md` §1) is asserted in documentation, never enforced in code.** Nothing today stops one person with service-role access from posting an unreviewed adjustment. Dual-approval is a real workflow to build, not a policy to trust.
- **`users.country` (the field "full user stat by location" needs) is itself only a build _target_** — `docs/02-DATA-MODEL.md` §9, part of the still-unbuilt multi-currency onboarding. Every user who signed up before that onboarding exists has `country = NULL`. Location analytics must be designed to handle that honestly (§8) rather than assume the column is already populated.
- **The "change earning from per-message to per-word" ask describes a capability that partially already exists and partially doesn't.** `docs/03-ECONOMY-LEDGER.md` §4's _current_ formula already bills by word count in blocks (`2 × ceil(words/50)`), not a flat per-message rate — so "per number of words" is already how billing works today. What genuinely doesn't exist is the ability to **swap the pricing _model_ itself** (not just retune its numbers) from an admin UI without an engineering release. §4 below designs that as a real, safely-scoped "pricing strategy" mechanism, not a way to hand-edit SQL from a browser.

## 3. What this is, architecturally — a new app, not a mode of the existing one

**`apps/admin/`** — a new workspace member, **Next.js (App Router) + TypeScript**, not an extension of the Expo mobile app and not a second Expo target. Reasoning:

- The mobile app's entire architecture (Zustand + TanStack Query, no server) is built around "the client never holds a trusted secret." An admin console is the opposite: it legitimately needs a server-side layer holding the service-role key, doing authorization checks, and never shipping that key to a browser. Next.js's Route Handlers / Server Actions are exactly this — a real backend-for-frontend, not a SPA calling Supabase directly with an anon key.
- Data-table-dense, keyboard-and-mouse, desktop-first UI (user lists, transaction grids, filter builders) is a different design problem from a phone's touch-first chat UI — reusing Expo Router here would fight the tool, not save time.
- **What genuinely gets reused, not rebuilt:** `packages/ledger-types` (the generated Postgres types, already shared-package-shaped per `docs/09-PROJECT-STRUCTURE.md`), `packages/payments` (the `PaymentProvider` interface — the Treasury withdrawal path in §5 calls the exact same `payout()` method `withdraw` already uses, never a second payment integration), and every `pricing_config` key / `SECURITY DEFINER` function signature already documented in `docs/02`/`docs/03` — the dashboard is a new _view and control surface_ over the existing financial engine, never a parallel one. A new `packages/admin-ui` isn't needed at v1; a standard component/table kit (shadcn/ui + Tailwind, the current default for exactly this class of app) is the pragmatic choice — no reason to hand-roll a design system for an internal tool the way the consumer app's `docs/04-DESIGN-SYSTEM.md` earns its own bespoke one.
- **Hosting:** Netlify, alongside the marketing site (`docs/15-MARKETING-SITE-PWA-SCOPING.md`) but as its **own separate Netlify site** on its own subdomain (e.g. `admin.involveme.com`), never bundled into the public marketing deploy — a build/deploy failure or misconfiguration on the public site must never be able to touch the admin surface's own access controls, and vice versa.

## 4. Super-admin capability: roles, pricing, and feature toggles

### 4.1 RBAC schema (new tables, additive — nothing existing changes shape)

- `admin_users`: `id, email, display_name, created_at, disabled_at (nullable), last_login_at`. **Deliberately not `auth.users`** — an admin identity is a completely separate namespace from a consumer phone-OTP account (an admin is never also a chat user under the same row), avoiding any chance of a consumer-side bug ever touching admin privilege.
- `admin_roles`: `id, name (e.g. 'super_admin', 'finance_admin', 'support_agent', 'compliance_officer', 'content_moderator', 'read_only_auditor'), description`. Seed with the roles below; a super admin can create new ones (§4.3) — the _permission model_ is fixed and reviewed, the _role names/combinations_ are configurable.
- `admin_permissions`: a fixed enum-like table of atomic capabilities (`view_users`, `edit_pricing_config`, `initiate_platform_withdrawal`, `freeze_wallet`, `resolve_fraud_signal`, `manage_admin_roles`, `view_treasury`, `view_reports_queue`, `moderate_content`, …) — atomic, not bundled, so a role is genuinely a chosen _set_ of these, not a hardcoded tier.
- `admin_role_permissions`: `(role_id, permission_id)` join table.
- `admin_user_roles`: `(admin_user_id, role_id)` — an admin can hold more than one role.
- `admin_audit_log` (append-only, same posture as `ledger_entries` — **no `UPDATE`/`DELETE` grant on this table, ever**): `id, admin_user_id, action, target_type, target_id, before_state (jsonb, nullable), after_state (jsonb, nullable), ip_address, created_at`. Every single write this dashboard makes — a pricing change, a wallet freeze, a role edit, a fraud-signal resolution — writes one row here in the same transaction as the actual change, via a `SECURITY DEFINER` function (see §7), never as an application-layer "best effort" log that a bug could silently skip.

**Default seeded roles**, matching the ask's own examples and this app's actual risk surface:

| Role                 | Can do                                                                                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `super_admin`        | Everything below, plus manage other admins' roles, edit the permission model itself, initiate platform treasury withdrawals                                                   |
| `finance_admin`      | View/adjust pricing_config, view treasury + all wallets, post manual ledger adjustments (dual-approved, §4.4), cannot manage admin roles                                      |
| `compliance_officer` | View KYC records, fraud_signals, user_reports; freeze/unfreeze wallets; cannot touch pricing or treasury                                                                      |
| `support_agent`      | View user profiles, thread metadata (never message _content_ by default — see §7.4), resolve user_reports at the "contacted user" level; cannot freeze wallets or touch money |
| `content_moderator`  | View `moderated_content` flagged queue, action content-policy violations; no financial access at all                                                                          |
| `read_only_auditor`  | View everything (analytics, treasury, audit log itself), write nothing — the role external counsel/an auditor gets                                                            |

### 4.2 Pricing & fee control (the "set payment percentage" ask)

A real UI over the `pricing_config` keys that already exist and are already documented as config-not-constants (`CLAUDE.md` rule #9): `platform_topup_fee_bps`, `platform_earning_take_bps`, `platform_transfer_take_bps`, `platform_group_message_take_bps`, `message_base_credits`/`message_word_block_size`/`message_max_words`, `credit_unit_kobo`, every withdrawal threshold. Every change:

1. Writes the new value; `pricing_config_history` already captures `old_value`/`new_value` automatically via its existing trigger (§2's correction) — what this phase actually adds is a real `changed_by` (the trigger hardcodes `'system'` today) and an `effective_at`, either by having the admin update function set a session-scoped identity the trigger reads, or by writing its own history row directly.
2. Requires dual sign-off above a configurable materiality threshold (e.g., any change to a take-rate bps value, ever; a `message_base_credits` tweak might not need it — the threshold list itself is a `super_admin`-editable table, not hardcoded, so ops can tune what counts as "material" without an engineering release).
3. Is never applied _retroactively_ — exactly like today's `pricing_config` design, a change only affects transactions computed after it lands; nothing about the ledger's already-settled history is ever touched, preserving `CLAUDE.md` rule #4 completely untouched by this feature.

**Free-vs-charged toggles** ("enable feature to charge or stay free") — **built 2026-09-24**, after Phase F, as a small standalone piece rather than part of Phase D: `/dashboard/pricing/services` surfaces every existing kill-switch as a real control — `group_chat_enabled` (currently `0`, per `docs/03-ECONOMY-LEDGER.md` §10, still correctly gated behind Phase 5's fraud infra regardless of this dashboard existing) and any future per-service on/off flag — as a single "Service Pricing" table: service name, current rate/status (free / charged at X), last changed by/when. Built as a curated code-level registry (`apps/admin/lib/servicePricing.ts`), not a new DB table — one real entry didn't justify standing up a registry table on spec; the day a second service toggle is actually needed (e.g. voice/video calls once `docs/11-VOICE-VIDEO-CALLS-SCOPING.md` is built) is the right time to revisit whether a real table earns its keep. Writes go through the same `fn_admin_update_pricing_config` every other non-`_bps` key already uses — no new write path, no new dual-approval decision.

### 4.3 "Introduce new features not yet set" — a pricing _strategy_ framework, scoped honestly — **built 2026-09-24** (schema/functions + `/dashboard/pricing/strategy` UI)

The literal ask (an admin-configurable switch between fundamentally different pricing _models_, not just retuned numbers within one fixed formula) is a real, buildable capability — but it must not become "write arbitrary billing logic from a text box," which would reopen every exploit `docs/06-SECURITY-FRAUD-LOOPHOLES.md` §1/§7 already closed. The safe version:

- `pricing_config.active_pricing_strategy` (new key) selects among a **small, fixed set of pre-built, pre-tested Postgres pricing functions** — e.g., `tiered_word_block` (today's model, `fn_price_message_tiered_word_block`), `flat_per_message` (`fn_price_message_flat`), `linear_per_word` (`fn_price_message_linear`) — each independently unit-tested with the exact ledger-conservation + concurrency coverage `CLAUDE.md` already mandates for anything touching money, _before_ it's ever selectable.
- `fn_send_message` dispatches to whichever strategy is active, reading it once per call (cached the same 60s window every other `pricing_config` read already uses) — the admin's actual day-to-day action is choosing among already-shipped, already-tested strategies and tuning their own parameters (block size, base rate, cap), never authoring new formula logic live.
- **A genuinely new strategy (a formula nobody has built yet) is still an engineering task** — this framework makes _switching_ instant and reversible without a release, it does not make _inventing_ a new billing model a no-code exercise, and this document says so plainly rather than overpromising a "build any pricing model from the dashboard" capability that would be reckless for a financial system.

### 4.4 Dual-approval workflow (closes the asserted-but-unenforced §2 finding)

`admin_pending_actions`: `id, action_type, payload (jsonb), requested_by, requested_at, approved_by (nullable), approved_at (nullable), status ('pending'/'approved'/'rejected'/'expired')`. A materially risky action (manual ledger adjustment above a threshold, a treasury withdrawal, a bps pricing change, disabling another admin) is _proposed_, not executed, by the requester; a **different** admin with the matching permission approves it before the underlying `SECURITY DEFINER` function actually runs. Mirrors the ledger's own "manual adjustments need a second sign-off" rule, but for real this time — enforced in the function itself (it checks for a matching approved-and-unexpired row), not just in a process document.

## 5. Treasury: platform revenue withdrawal (the genuinely new capability)

This is new, not a UI over something that already exists — see §2's finding.

- **`fn_initiate_platform_withdrawal(p_admin_id, p_currency, p_amount_minor, p_bank_account_ref)`** (`SECURITY DEFINER`, `super_admin`-only, dual-approved per §4.4 with **no materiality floor** — every platform withdrawal requires two admins, no exceptions): debits `platform_revenue_topup_fees`/`platform_revenue_earnings_cut` (per-currency, per `docs/02-DATA-MODEL.md` §9's multi-currency target) by the requested amount, in the same fixed-ascending-wallet-lock order every multi-wallet function already uses, and calls `packages/payments`' existing `payout()` — the **same interface** `withdraw` already calls, not a second payment integration — to move real money to InvolveMe's own registered company bank account (a `platform_bank_accounts` table, company-owned destinations only, never a user's).
- **Never touches the reserve wallets** (`platform_reserve_*`) — by design, matching `docs/02-DATA-MODEL.md` §5's own stated purpose: the reserve exists specifically to sit there, unspent, for chargeback self-insurance. A separate, explicitly-labeled "release reserve" action can exist later if the business ever needs it, but it is not part of this phase and should require its own, higher bar of approval if it's ever built.
- **Treasury view**: real-time (Realtime-subscribed, same mechanism the mobile wallet tab already uses) balance of every platform-owned wallet, by currency, plus a running chart of revenue vs. reserve accumulation over time and a full withdrawal history — the first time anyone at InvolveMe can see "what does the company actually have available to withdraw" without a raw SQL query.
- **Reconciliation stays exactly as-is** (`docs/02-DATA-MODEL.md` §4) — the hourly job already pages on any `sum(ledger_entries) != wallets.balance` mismatch; treasury withdrawals go through the same `ledger_entries`-first mechanism as every other balance change, so they're covered by that guarantee automatically, not a new one.

## 6. Reports & fraud review queue

Two existing, currently-invisible tables get their first real UI:

- **Fraud signals queue** (`fraud_signals`): filterable by signal type/severity/date, shows the flagged pair/user with enough context to actually decide (recent transaction history, shared device fingerprints, KYC status) without a second tool. Actions: freeze wallet (`is_frozen`, already the exact flag every spend/withdraw path already checks — the dashboard is the first thing to ever _set_ it outside Studio), dismiss with a reason, escalate. **No auto-action ever fires from this queue** — matching the explicit standing product decision `docs/06-SECURITY-FRAUD-LOOPHOLES.md` §12 already records ("fraud signals are for manual review, never auto-freeze") — a human always clicks the button.
- **User reports queue** (`user_reports`): filterable by reason/date/reported-user, one-click to the reported user's profile and the thread it happened in (if any), resolution actions (warn, suspend `is_suspended`, ban, dismiss) each writing to `admin_audit_log`.
- **Content moderation queue** (`moderated_content`, once a real `OPENAI_API_KEY` is live per `docs/07-COMPLIANCE-LEGAL.md` §3/§6): flagged (not blocked) content for human review, same posture as the two queues above.

## 7. Security architecture — the part that matters most

1. **Admin authentication is fully separate from consumer auth.** Email + password + mandatory TOTP-based MFA (no SMS OTP for admins — SIM-swap risk is exactly the kind of thing worth taking seriously on an account that can move real money) via Supabase Auth's own second, admin-scoped project or a separate auth table entirely — never the same `auth.users` phone-OTP flow a chat user goes through.
2. **The admin backend never ships the Supabase service-role key to the browser.** Every admin action is a Next.js Server Action / Route Handler that holds the key server-side, checks the calling admin's session + permission set, then calls the relevant `SECURITY DEFINER` function — the exact same "client never trusted, function validates everything" shape `CLAUDE.md` rule #1 already mandates for the consumer app, extended here rather than reinvented.
3. **Every new `SECURITY DEFINER` function this phase adds follows `CLAUDE.md` rule #11 from its very first migration** — explicit `revoke ... from public, anon, authenticated` + `grant ... to service_role`, in the same migration as `create function`, no exceptions, matching the hard lesson already paid for once in this codebase (`20260915161500_lock_security_definer_execute_grants.sql`).
4. **Message content is not visible to every role by default.** `support_agent` sees thread _metadata_ (participants, timestamps, credit amounts, block/report status) to help a real support case, not a general "read anyone's DMs" capability — a genuine privacy commitment worth stating explicitly, and a real design constraint on the reports queue's own UI (show the _reported_ message for the specific report being reviewed, backed by its own narrowly-scoped RLS/function, never a blanket message-search-everyone feature).
5. **IP allowlisting** (optional per admin, enforced at the Next.js middleware layer) and **session timeout** (short-lived sessions, re-auth for high-risk actions like a treasury withdrawal even mid-session) — standard practice for a console with this blast radius.
6. **Rate limiting and anomaly alerting on the admin surface itself** — an admin account behaving unusually (bulk exports, a spike in wallet freezes, a login from a new country) should page someone, the same instinct `docs/06-SECURITY-FRAUD-LOOPHOLES.md` already applies to consumer accounts, applied to the more dangerous account class here.
7. **`admin_audit_log` is the product's own second ledger** — append-only, no `UPDATE`/`DELETE` grant for any role, reviewable by `read_only_auditor`. If counsel or a regulator ever asks "who did what, when," this table is the complete, honest answer.

## 8. User analytics, location stats, and search — built for real traffic

- **Location stats**: grouped by `users.country` where present; every pre-existing user without it (§2's finding) is bucketed as "Unknown" honestly rather than guessed at silently. Recommended backfill: a best-effort, passive IP-based reverse-geocode pass over historical sign-in IPs (if Supabase Auth logs retain them) run once as an admin-triggered batch job, clearly labeled as an estimate — never presented with the same confidence as a user's own onboarding-confirmed country.
- **Search**: every list view (users, transactions, threads, reports, admins) gets real server-side, indexed search (Postgres full-text/`pg_trgm` where appropriate — `pg_trgm` is already a dependency of this project per `docs/06-SECURITY-FRAUD-LOOPHOLES.md` §6, not a new one) with pagination from day one — **never** a "load everything and filter client-side" table, which is the single most common way an internal tool quietly falls over the first time the users table crosses six figures.
- **Traffic-scale defaults**: cursor-based pagination everywhere (not offset — offset pagination degrades badly on large, frequently-changing tables like `ledger_entries`), server-side aggregation for every chart (never "fetch all rows, sum in the browser"), and a hard cap + async CSV-export job for any bulk data pull instead of a synchronous "export everything" button that can time out or take the database with it.

## 8.1 Addendum (2026-09-20, pre-Phase-A engineering review): four gaps found, closed before any code

A full pass against the actual codebase (migrations grepped directly, not assumed) confirmed `fraud_signals`/`user_reports` still have zero client grants, `fn_initiate_withdrawal` is still scoped to user wallets only, `pg_trgm` is enabled, and no `admin_*` table exists yet — but also caught that this document's own earlier claim about `pricing_config_history` not existing was itself wrong (corrected in §2 and §4.2 directly: the table and its audit trigger are real, just anonymous). The design itself (RBAC, dual-approval, append-only audit, phase ordering) stands. Four things Phase A specifically needs decided before it can start, none of which the original pass addressed:

1. **Bootstrap chicken-and-egg.** §9 Phase A's exit criteria ("a super admin can log in, create a second admin") presupposes a first super_admin already exists — but by definition no admin row exists yet to grant that role through the dashboard's own UI, and the dashboard must never expose a public "sign up as admin" endpoint. Resolution: a one-time seed script (`scripts/create-first-admin.ts`, run manually against `SUPABASE_SERVICE_ROLE_KEY`, never deployed as a route), documented in `apps/admin/README.md`. Run once per environment; the script refuses to run if any `admin_users` row already exists.
2. **Admin auth mechanism, decided.** §7.1 left "a separate Supabase Auth project or a separate auth table entirely" open. Decision: **a dedicated `admin_users` table**, not a second Supabase Auth project — password hashing, TOTP (RFC 6238) via a standard library, session as a signed short-lived httpOnly cookie (JWT, `jose`) minted by a Server Action and verified in Next.js middleware on every request. Reasoning: a second Auth project is a second thing to provision, fund, and keep credential-rotation policy straight on, for a handful of internal accounts — `CLAUDE.md` rule #10 ("stay lite," check whether existing tooling already covers it before adding infra) argues directly against it here. The custom table costs more application code (login verification, session signing) but zero new infrastructure. **Implementation deviation, decided while building Phase A piece 3:** password hashing uses Node's built-in `crypto.scrypt`, not a native argon2 package — same memory-hard-KDF security property, but zero new native-compiled dependency in an environment where that's a real install-time risk, and it matches this codebase's own existing precedent (`two_step_pin_hash` already uses built-in-crypto + a pepper rather than a hashing library). Recovery codes get a plain SHA-256, adequate given their own high entropy (~50 bits, machine-generated, not human-chosen).
3. **MFA recovery path.** Mandatory TOTP with no recovery story is a real lockout waiting to happen, not a hypothetical. At enrollment, generate 10 single-use recovery codes, store only their hashes, show the plaintext once. Losing both device and codes requires a **different** `super_admin` to reset the locked-out admin's MFA enrollment (writes `admin_audit_log`, same as every other admin action). The bootstrap admin's own recovery (no second super_admin exists yet to do this for them) is a documented manual break-glass procedure — direct DB access via service role to clear their `totp_secret`/force re-enrollment on next login — same access level Supabase Studio already has today, but now happening against a table that logs it after the fact instead of leaving zero trace.
4. **CI/deploy wiring.** `apps/admin` joins the existing `workspaces: ["apps/*", "packages/*"]` array as a normal member; the repo's `lint-and-typecheck` CI job already runs `turbo run lint`/`turbo run typecheck` across every workspace unconditionally (confirmed in `.github/workflows/ci.yml`), so it covers the new app automatically the moment it has `lint`/`typecheck` scripts — no CI file changes needed for that part. What Phase A does need and can't do unattended: a **new Netlify site** on its own subdomain (§3's `admin.involveme.com`) provisioned in the Netlify dashboard, and that site's environment variables (`SUPABASE_SERVICE_ROLE_KEY`, session-signing secret, etc.) set there directly — never committed, never passed through the public marketing site's config. This is a manual step on your end when Phase A is ready to deploy past local dev; flagging it now so it isn't a surprise mid-phase.

## 9. Build phases (for your review — nothing starts until you say go on a specific phase)

**Phase A — Admin identity & RBAC foundation (highest priority; nothing else in this doc can safely exist without it)**
Schema from §4.1, admin auth (email+password+TOTP), the permission-check middleware, `admin_audit_log` wired from day one even before there's much to log. Exit criteria: a super admin can log in, create a second admin with a limited role, and every action either of them takes produces a real audit row.

**Phase B — Read-only visibility: users, wallets, transactions, treasury**
Every existing table becomes _viewable_ (search, filter, pagination per §8) before anything becomes _editable_. Includes the Treasury view (balances + history) but not yet the withdrawal action itself. Exit criteria: an ops person can answer "what does this user's wallet look like and why" and "what does the company currently hold in revenue" without opening Supabase Studio.

**Phase C — Reports & fraud review queue (closes the Phase-5-flagged gap directly)**
§6 in full — the two currently-invisible queues get real UI and real (manual-only) actions.

**Phase D — Pricing & service controls**
