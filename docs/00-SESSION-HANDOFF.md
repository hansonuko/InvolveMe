## Snapshot as of 2026-09-14 (session 11 — full Settings, real blocking/reports, push notifications, read receipts)

PR #26 merged first (per explicit request). Then a genuinely large ask — "build the full settings... privacy, last seen, media, notifications... add settings for any real gap... build in push notifications exactly like WhatsApp" — was scoped honestly before building rather than filled in with fake toggles: about a third of "full WhatsApp settings" would have been UI with nothing real behind it (no media pipeline anywhere in this app, no presence tracking, no push infra yet). Presented the split (what's real and buildable now vs. what needs new infra vs. what's out of scope and why) and asked four targeted questions before writing code. All four came back "recommended": push notifications for new messages only (not all events), skip last-seen/presence, defer avatar upload, and account deletion as a support-request queue (not instant self-service, given this app custodies real money).

**New migration `20260914090000_settings_privacy_reports_push.sql`:**

- **Real blocking, finally** — the single most interesting gap found this pass: `threads.is_blocked` and its enforcement inside `fn_send_message` (reject with `thread_blocked`) had existed since Phase 1, but **nothing anywhere ever set it**. There was no way to actually block someone, despite the column and the guard both being live and tested. Replaced the boolean with `blocked_by` (who blocked it — needed for a "Blocked contacts" list and to stop a blocked person unblocking themselves) and added `fn_set_thread_blocked` + `set-thread-blocked` Edge Function. `fn_send_message` re-created (`create or replace`, forward-only) against the new column.
- `read_receipts_enabled` on `users` (default `true`) — real privacy toggle over data that already existed (the read-cursor built two sessions ago for unread counts). Turning it off doesn't stop the cursor from being written (your own unread-badge accuracy shouldn't depend on whether you share it with others, same as WhatsApp's actual behavior) — it stops `thread/[id].tsx` from _rendering_ a read indicator to the other participant, gated client-side on the partner's own flag.
- `push_tokens` table — one row per device, RLS lets the client upsert/delete its own rows directly (no `SECURITY DEFINER` needed for a self-scoped non-money write). Deliberately no `users.push_notifications_enabled`-style column: "off" is just "no token row," one source of truth instead of two that could disagree.
- `user_reports` and `account_deletion_requests` — both insert-only-own via RLS, neither readable back through the app (ops/admin review only). The reporting system is an actual app-store review requirement (`docs/07-COMPLIANCE-LEGAL.md` §4) that was previously entirely missing.

**Push notifications — real pipeline, new-message events only (as scoped):** `expo-notifications` + `expo-device` installed, `lib/push.ts` handles permission request/token registration (only ever prompted from the explicit Settings toggle, never on app launch — a silent `resyncPushTokenIfPermitted` on login re-registers an _already-granted_ token without prompting again). `supabase/functions/_shared/push.ts`'s `sendPushToUser` posts to Expo's push API directly (no SDK needed) and is wired into `send-message` via `EdgeRuntime.waitUntil` so a slow/failed push provider can never delay or fail the billing-critical response it's piggybacking on. `app.json` gained the `expo-notifications` config plugin, reusing `android-icon-monochrome.png` (built during the app-icon pass) as the Android notification icon — Android requires a white-alpha silhouette for exactly this, which that asset already was.

**Full Settings screen rebuilt** (`app/settings/index.tsx`): Profile (name/about — both already client-updatable columns, no new backend), Account (KYC status, unchanged; delete-account request), Privacy (read receipts toggle, Blocked contacts list, Report a user), Notifications (push toggle with real permission-denied messaging), Help (Invite a friend via the native share sheet, a "Terms & Privacy" row that honestly says "not yet published" rather than linking to a policy that doesn't exist, app version from `expo-constants`).

**Thread screen gained a real overflow menu** (block/unblock, report) — the natural place WhatsApp/Telegram put these, not just buried in Settings. Composer disables with an honest placeholder when the thread is blocked (either direction). **Read receipts are live**: own messages show a single check (sent) or double check (`Ionicons` `checkmark-done`) once the partner's read cursor has passed that message's timestamp — real data, gated on the partner's actual privacy flag.

**Explicitly not built, per the scoping conversation, not oversights:** last-seen/online presence (no tracking infra, would need a heartbeat mechanism), avatar photo upload (needs a Storage bucket — first media feature this app would ever have), media/network-usage settings (nothing to configure without a media pipeline), two-step verification PIN (doesn't map to phone-OTP-only auth), change phone number (a real re-verification flow, not a Settings field), push events beyond new messages (credit received, top-up confirmed, withdrawal completed — same mechanism would work, just not wired this pass).

**Verified:** `tsc --noEmit`/`expo lint` clean. Full `npm run test:functions` (all 9 files, including new `set-thread-blocked-function.test.js`, 12/12), `npm run test:db` (22/22), `npm run test:group-chat` (19/19) all re-run clean — confirms the `threads.is_blocked` → `blocked_by` migration and `fn_send_message` re-creation didn't regress anything already built. `send-message` and `set-thread-blocked` deployed.

**Docs updated for real gaps found, not just new features:** `docs/07-COMPLIANCE-LEGAL.md` §4 now states plainly which app-store-review items are done (reporting/blocking) vs. still genuinely missing (content moderation, ToS/Privacy Policy, age verification) — an honest status line, not a silent "will build."

## Snapshot as of 2026-09-14 (session 7 — unread/read-cursor tracking, real end to end)

Per the explicit "start with unread/read-cursor tracking" call, after reviewing what's naturally next post-rebrand. This is a real, complete feature — not scoped-and-parked like the group-chat billing model — because unlike that one, there was no open product decision blocking it: read-cursor tracking has one obvious correct shape (per-participant last-read timestamp, unread = messages from the other side sent after it) and no money involved.

**New migration `20260914080000_thread_read_cursor.sql`:**

- `threads.participant_a_last_read_at`/`participant_b_last_read_at` (nullable timestamptz, `null` = never read) — a column pair rather than a separate `thread_reads` table, since this schema's threads are strictly 1:1; a generic per-user-per-thread table would just be `threads` with extra steps. Group chats would need their own version of this if `group_chat_enabled` ever flips on (a `group_members.last_read_at` column fits that N-member shape better) — not scoped now, not needed while that feature is gated off.
- `thread_unread_counts` — a `security_invoker = true` view computing, per caller, unread messages per thread (sender ≠ caller, sent after the caller's own cursor). The `security_invoker` flag is load-bearing, not stylistic: without it, the view would run with the migration role's RLS bypass rather than the querying user's, silently exposing every thread's unread count to everyone. Confirmed the view's `auth.uid()`-scoped behavior via real authenticated REST calls in the test suite, not just reasoned about — a raw pg admin connection has no JWT claims to test this with.
- `fn_mark_thread_read(thread_id, caller_id)` (`SECURITY DEFINER`) sets _only_ the caller's own cursor column. Deliberately not a client-writable RLS policy + column grant: Postgres column-level grants aren't conditional on which participant slot the caller occupies, so that shortcut would let participant A clear participant B's unread badge on their shared thread (RLS's row check would pass, since A does legitimately own the row).

**New Edge Function `mark-thread-read`** — thin wrapper, same `_shared/auth.ts` JWT-verification posture as every other function here even though nothing financial is involved. Called on opening a thread.

**Tested:** new `supabase/tests/mark-thread-read-function.test.js` (wired into `npm run test:functions`), **10/10** — auth/validation errors, the view's per-caller scoping (own messages never count as unread to yourself, another participant's cursor can't be touched), and a real ledger-adjacent-but-not-financial correctness case (a message sent after the cursor is unread again, the earlier now-read one isn't double-counted). Design choices made to keep this on the app's _existing_ audited rails rather than inventing a second money-movement path (full rationale in `docs/03-ECONOMY-LEDGER.md` §9):

- New migration `20260913091500_credit_transfer_between_users.sql`: `credit_transfers` table (own-rows RLS, no client writes — same posture as `topups`/`withdrawals`), two new `pricing_config` keys (`platform_transfer_take_bps` = 2000 default, independently tunable from the escrow-release take rate it mirrors; `credit_transfer_max_credits` = 1000, a blast-radius cap on a brand-new money-moving path, not a product decision), and `fn_transfer_credit` (`SECURITY DEFINER`).

- Locks every wallet it touches (sender's `topup_credit`, recipient's `earnings_pending` + `withdrawable_cash`, the platform's `platform_revenue_earnings_cut`) in a single fixed ascending-wallet-id order before touching any of them, per `docs/02-DATA-MODEL.md` §3 — necessary here specifically because, unlike every other wallet function so far, this one locks _two different users'_ wallets in the same call, so a concurrent A→B and B→A transfer could otherwise deadlock by taking the same two rows in opposite order.
- New Edge Function `transfer-credit`: auth → resolves `recipient_phone` the same way `find-user-by-phone` does → calls `fn_transfer_credit` → maps its exceptions to HTTP status (mirrors `withdraw`'s `mapInitiateWithdrawalError` prefix-matching convention). ### Incident: a real ₦100 top-up stuck unconfirmed for 1+ hour — root cause and fix

The user paid real money for chat credit; the payment succeeded on Flutterwave's side, but the credit never landed. Diagnosis, in order:

1. `public.webhook_events_seen` was **completely empty** — not just for this topup, ever. No webhook had ever been received by this project, for any event, since the table was created.
2. Confirmed independently via Flutterwave's own API (`GET /charges?customer_id=...`) that the payment genuinely succeeded (`status: "succeeded"`, real charge id, the user's real name as `originator_name`) — the money was never at risk, Flutterwave just never told us.
3. Manually probing the deployed `webhook-flutterwave` URL directly (not `deno run` locally — every existing test in this suite only ever did that) surfaced the real cause immediately: **HTTP 401 `UNAUTHORIZED_NO_AUTH_HEADER` from Supabase's own platform-level Edge Function gateway**, before this project's code ever ran. `webhook-flutterwave` had been deployed with the platform's default JWT-verification gate enabled — correct for every other function (called by the app with a real user session), wrong for this one specific function, which is server-to-server and will never carry a Supabase auth header. This has been broken since the very first batch deploy of all 5 functions together, several sessions ago — nobody had passed `--no-verify-jwt` for this one function specifically, and nothing in the test suite would ever have caught it, since every test spawns the function locally rather than calling the real deployed URL.
4. Fixed: `supabase functions deploy webhook-flutterwave --use-api --no-verify-jwt`. Confirmed via the Management API (`GET /v1/projects/.../functions/webhook-flutterwave` → `"verify_jwt": false`) that this is a **persisted per-function platform setting** — but the flag still needs to be included on every future deploy of this function to be safe, since its stickiness across a deploy that omits the flag isn't something worth testing by accident.
5. Redeploying past the gateway surfaced a **second, independent bug**: a real 500 crash. `packages/payments/flutterwave.ts`'s `verifyWebhook` used the global `Buffer` with no explicit import — tolerated by a local `deno run`, not tolerated by Supabase's deployed edge-runtime. Fixed with `import { Buffer } from 'node:buffer'`. Confirmed via `grep` that this was the only unguarded-global-`Buffer` instance anywhere in the Deno-side codebase.
6. **The user's money**: fixed directly by calling `fn_confirm_topup` with the real Flutterwave charge id — the exact same idempotent, ledger-safe DB function the webhook would have called, using data independently confirmed from Flutterwave's own API. Not a manual balance edit; fully auditable through the normal ledger (`topup_purchase` ledger entry, `ref_type: topup`, `ref_id` matching the real topup row). Credits landed, topup marked `completed`.
7. Attempted to prove the _full_ real pipeline via Flutterwave's own `POST /resend-webhook` (`{ id: "chg_...", type: "charge.completed" }`, confirmed `200 success` from Flutterwave) — this never actually arrived at `webhook_events_seen` even after both bugs were fixed and directly-probed synthetic requests worked perfectly. Left unresolved and explicitly flagged, not silently assumed fine: either Flutterwave's resend has more latency than observed here, or there's a subtle mismatch in the dashboard-saved webhook URL/secret that only a real future transaction (or the user re-checking the dashboard fields directly) will surface. **Whether a real webhook now lands successfully is unconfirmed — the endpoint is proven healthy, Flutterwave's delivery to it is not.**
8. **New regression test**: `supabase/tests/webhook-flutterwave-deployed-smoke.test.js` (`npm run test:deployed`) — the first and only test in this suite that calls the real deployed URL instead of spawning the function locally. This is a permanent gap-closer: it would have caught both bugs above on day one. Every other test file's 87/87 "passing" said nothing about whether the deployed function actually worked.

**Lesson recorded for future sessions**: passing every local `deno run`-based test proves the _code_ is correct; it proves nothing about whether the _deployed_ function is reachable or configured correctly on the actual platform (JWT gate settings, secret propagation, runtime API differences). Any function this project cares about being reachable by an external, non-app caller (webhooks, in particular) needs at least one test that hits its real URL.

### Bugs this test suite caught in itself before it caught anything in the functions

Worth recording because they're exactly the kind of test-infrastructure mistake that quietly invalidates a test suite's results if not caught:

1. **Cross-user cleanup ordering.** A thread's messages can have `sender_id` pointing at _either_ participant, so tearing down "everything belonging to user X" one user at a time left the other participant's messages dangling and blocked the thread delete with an FK violation. - **Frozen-wallet enforcement, added this session after noticing it didn't exist:** `fn_send_message` now rejects a frozen payer wallet, `fn_release_escrow` now rejects a frozen payee wallet (and the whole `fn_send_message` call rolls back — the payer isn't charged for a reply that fails to release), `fn_confirm_topup` and `fn_initiate_withdrawal` reject frozen wallets too; `fn_refund_expired_escrows` skips (not aborts) a frozen payer's escrow so the bulk sweep still processes everyone else

### The gap that made item 5 necessary to extend beyond its original scope

`fn_run_reconciliation_check` sets `wallets.is_frozen` on a mismatch, but nothing anywhere actually _checked_ that flag — freezing a wallet did nothing to stop further activity on it, which defeats the point per `docs/02-DATA-MODEL.md` §4. Added `is_frozen` guards to every wallet lock in every money-moving function (`20260912082046_guard_frozen_wallets.sql`, `CREATE OR REPLACE` — no function signatures changed, so grants/permissions carried over automatically). Not something the roadmap called out as its own item; found while writing this doc's summary of item 5, on the theory that it belongs with the reconciliation check rather than as a separate future fix.

### Two things intentionally left as documented gaps in item 5 (not silent, not blocking)

- **"Notify" half of "hold and notify" isn't implemented.** A user without a verified bank account is correctly excluded from the auto-sweep, but nothing pushes them a reminder to add one — that needs an Edge Function + push service that doesn't exist yet.
- **Reconciliation "pages on-call" isn't implemented either** — a mismatch freezes the wallet and logs a high-severity `fraud_signals` row, which is the detectable/actionable part, but nothing pages anyone; that needs an external alerting integration.
- **The auto-sweep's "how long has this sat unwithdrawn" check uses `wallets.updated_at` as a proxy**, which is exact only when withdrawals always take the full balance (which `fn_initiate_withdrawal` defaults to). A partial withdrawal would reset the clock on older money still in the same wallet. Documented in the migration; exact per-credit aging would need dedicated tracking this migration doesn't add.

### Phase 1 items 2+3 — what was verified, not just written

Ran against the real dev database with two real test users (created via the Admin API, then fully cleaned up in FK-safe order — confirmed zero rows left in any table afterward, platform wallets reset to 0):

- `fn_buy_credit` on a ₦1,000 top-up computes exactly ₦20 fee / 98 credits; `fn_confirm_topup` issues them and is a no-op on a retried/duplicate call (webhook-retry safe)
- `fn_start_thread` is find-or-create, not create-every-time
- A (payer) sends a 30-word message → 2 credits charged, escrowed, **not** yet earned by B
- B (payee) replies with a 60-word message → 4 more credits charged to A, **and** releases both the earlier escrow and this new one in the same call (per docs/03 §5's "up to and including this exchange") — A ends up debited 6 credits total, B ends up with **5000 kobo in `withdrawable_cash`**, platform earns **1 credit**, `earnings_pending` nets back to zero (auto-converted immediately, matching the doc's worked-example rounding exactly: 2×80%→2/0, 4×80%→3/1)
- Insufficient-balance and >500-word messages are both rejected with the expected error codes
- `fn_initiate_withdrawal` debits `withdrawable_cash` immediately; `fn_fail_withdrawal` correctly reverses that debit and marks the withdrawal `failed` (the compensating path for when a provider transfer call fails after the DB already committed)
- Withdrawal below the ₦500 minimum is rejected without the bypass flag; a KYC-tier-0 user is rejected outright
- Anon key still gets zero rows / denied writes on every table (RLS posture unchanged by adding read policies for `authenticated`)

### Two real bugs found and fixed during this build (not hypothetical — both would have shipped broken otherwise)

1. **`make_interval(hours => v_refund_hours)` failed at runtime** — `pricing_config.value` is `bigint`, `make_interval` wants `integer`, and Postgres won't implicitly narrow in a named-argument function call. Fixed with an explicit cast. Caught by actually calling the function, not by the migration applying cleanly (DDL applies fine; the bug only shows up when the function body executes).
2. **Earnings never actually became withdrawable.** The original function only credited `earnings_pending` at escrow release and stopped there — nothing converted it to `withdrawable_cash`, contradicting docs/03-ECONOMY-LEDGER.md §6's "automatically and immediately on release." Fixed by adding the conversion as two more ledger legs in the same release transaction (debit `earnings_pending`, credit `withdrawable_cash`, both reason `earnings_conversion` — which is exactly why that reason already existed in the item-1 CHECK constraint enum).

### One schema correction made mid-session (forward migration, nothing hand-edited)

The item-1 schema had a single `platform_revenue` wallet kind, but top-up fees are cash (kobo) and earnings-take fees are credits — two different units that can't share one balance without silently mixing them. Split into `platform_revenue_topup_fees` and `platform_revenue_earnings_cut` via a new migration (`20260912072739_extend_schema_for_functions.sql`), which also added the `withdrawal_refund_failed` ledger reason needed for `fn_fail_withdrawal`.

### One workflow mistake worth remembering for next time

Pre-created all four migration files via `supabase migration new` before writing their content, then ran `supabase db push` — which applied the still-empty files and marked them "applied" in the remote's migration history. Editing them afterward meant `db push` would silently skip the real content on the next run (matches by filename/timestamp, not content). Fixed by deleting the stale rows from `supabase_migrations.schema_migrations` and re-pushing, but the correct sequence is: **write a migration's full content before pushing it, not batch-create-then-fill.**

### A schema behavior worth knowing, not a bug

`threads.participant_a/b` reference `users(id)` **without** `ON DELETE CASCADE` (unlike `wallets`, which does cascade from `users`). This means a user with any thread history can't be hard-deleted — consistent with `ledger_entries` already being permanently undeletable once it exists. For a money-moving app this is probably the right default (can't erase transaction/conversation history via account deletion), but it means "delete a user" will need to become "suspend/anonymize a user" as a product decision later, not literal `DELETE FROM users`.

## Key decisions on record (deviations from the original verbal brief — don't "fix" these back without re-reading why)

1. **Stack:** React Native (Expo) + Supabase (Postgres/Auth/Realtime) + Flutterwave-first with Paystack provisioned behind a `PaymentProvider` interface. User-selected from options presented; see conversation history if the reasoning matters later.
2. **Message pricing is tiered**, not flat: `2 × ceil(words / 50)` credits with a 500-word hard cap — the literal brief's flat "+2 credits over 50 words, no cap" is exploitable (see `docs/06-SECURITY-FRAUD-LOOPHOLES.md` §1). Matches the brief exactly at the two points it specified (≤50 words, just-over-50). **Now implemented and verified** in `fn_send_message`.
3. **Escrow mechanic added, not in the original brief:** credits charged to the payer are held until the payee actually replies, auto-refunded if unanswered after 48h. Closes a fairness gap (payer charged into a void) the literal brief didn't address. **Now implemented** (`fn_send_message` + `escrows` table); `fn_refund_expired_escrows` exists but isn't cron-scheduled yet (item 5).
4. **Earnings auto-convert to cash immediately** on escrow release (fixed ₦10/credit rate) rather than requiring a manual "convert" step with a floating rate — simplification, see `docs/03-ECONOMY-LEDGER.md` §6 for why. **Now implemented and verified** in `fn_release_escrow`.
5. **Web target de-scoped.** Expo's template defaults to web + static SSR export; that crashed under Node SSR (AsyncStorage touches `window`) and was never actually a v1 goal (WhatsApp-shaped app is mobile-first). Switched to `single` (client-only) output. See PR #1.
6. **2% top-up fee likely doesn't cover the payment gateway's own processing fee** — flagged as an unresolved business-model question in `docs/03-ECONOMY-LEDGER.md` §3, not something the code can fix. Needs a real decision before launch (subsidize it, raise it, or floor top-up amounts).
7. **The `escrow_hold` ledger reason (from item 1) is deliberately unused.** A separate clearing-account ledger leg at hold time would need its own wallet abstraction; the `escrows` table itself already records what's held, and the per-wallet reconciliation invariant CLAUDE.md cares about doesn't require it. Documented in the functions migration's header comment.
8. **`wallet_float_kobo` dust-carry mechanic (docs/03 §3) is not implemented.** Top-up rounding remainders (sub-10-kobo) are currently just not credited anywhere — a real, small, deliberately-deferred gap, not silently dropped.
