### A real `eas update` bug, found the moment the user tried to log in after the first OTA push

The first `eas update` after OTA was wired up shipped a bundle missing `EXPO_PUBLIC_SUPABASE_URL`/`ANON_KEY` — the app fell back to its `placeholder.supabase.co` default and every network call DNS-failed. Root cause: `eas update --environment <env>` reads from **EAS's own hosted environment-variable store** (`eas env:set`/`eas env:list`), a completely different mechanism from `eas.json`'s `build.<profile>.env` block that `eas build` reads — setting one doesn't populate the other, and nobody had run `eas env:set` yet. Fixed by setting `EXPO_PUBLIC_SUPABASE_URL`/`ANON_KEY` across all three environments (development/preview/production) and re-publishing. **Before running `eas update` again, always confirm `eas env:list --environment <target>` actually shows what the app needs.**

### KYC vendor decision resolved: Prembly, Tier 1 only (not the camera/liveness widget)

The user provided real (live, prefix `live_`) Prembly credentials and initially pasted Prembly's `react-native-identity-kyc` widget integration snippet — a **native module** with camera/liveness capture (Android manifest wants CAMERA/RECORD_AUDIO/VIDEO_CAPTURE), which is Tier 2 per `docs/02-DATA-MODEL.md`, more than `withdraw` actually needs (Tier ≥ 1), and would need a new native build (triggering the "ask before building" rule) plus knowing what the widget's dashboard-configured `config_id` actually verifies. **Confirmed live before building anything** (same discipline as the Flutterwave research): a real BVN Basic call against a documented sample number returned a real `"Record not found"` — proving auth/reachability without needing real PII — plus a critical finding neither doc excerpt showed: **every Prembly verification call is billed (~₦45), success or failure.** Flagged to the user before spending more of their money on speculative test calls; they chose to spend one real ₦45 confirming the actual happy path with their own real BVN. **New: `packages/kyc/` (provider.ts + prembly.ts)**, mirroring `packages/payments/`'s interface pattern (CLAUDE.md rule #5's spirit, extended here even though that rule is written about payment providers specifically — `kyc_records.provider` already anticipated more than one vendor). `verifyIdentity()` covers both BVN Basic and NIN Basic, synchronous, no webhook needed.

**New Edge Function `submit-kyc`:** auth → `KycProvider.verifyIdentity()` → hashes the raw BVN/NIN with a server-only pepper (`KYC_HASH_PEPPER`) before it ever touches a row (never raw, per `docs/07` §5) → writes `kyc_records` → bumps `users.kyc_tier` to 1 on success. A watchlist match is blocked (no tier bump) and logged to `fraud_signals`, not surfaced to the user as anything different from a generic failure — standard sanctions-screening practice, per `docs/07` §2's "block or flag, never silently allow."

**A real gap found while scoping the _next_ function, not this one:** `kyc_records` had nowhere to put the verified name, but `link-bank-account` needs it to name-match against a bank account — and it can't be recovered from the (deliberately one-way) `bvn_or_nin_hash`. New migration `20260913080419_kyc_records_verified_name.sql` adds `verified_first_name`/`verified_middle_name`/`verified_last_name` (nullable, only set on a verified record) — a legal name is materially less sensitive than a raw BVN and is exactly the retention this compliance function requires, not scope creep.

**`PaymentProvider` interface extended** with `listBanks()`, `resolveBankAccountName()`, `createTransferRecipient()` — the three Flutterwave calls `link-bank-account` needs, confirmed against live docs (`GET /banks`, `POST /banks/account-resolve`, `POST /transfers/recipients` — the last one already anticipated correctly back in Phase 2 batch 2's schema design, per `PayoutRequest`'s existing comment).

**New Edge Function `link-bank-account`:** the flow that actually populates `bank_accounts.provider_account_id` for a real user — nothing had ever called this before this session; every previous test used a manually-inserted fixture. Resolves the account's registered name via Flutterwave, name-matches it (order-independent token match — Nigerian BVN records and bank names don't agree on name order) against the user's KYC-verified identity, and only on a match creates a real Flutterwave transfer recipient and writes `bank_accounts`. Per CLAUDE.md rule #7, a name mismatch is a **hard rejection**, not a row inserted with `name_match_verified: false` for later review — there's no admin-review flow for that state yet, so "nothing was linked" is the safer failure mode than "something ambiguous was linked." A mismatch also logs to `fraud_signals`.

**A real error-mapping bug caught while writing this function's test, not by review:** the first version mapped every Flutterwave failure (including a plain invalid-account-number rejection, a 4xx) to a 503 "provider unavailable" — telling the user to retry a request that would fail identically every time. Fixed to distinguish 4xx (real input problem → 400 `invalid_account`, don't retry) from a genuine 5xx/network failure (503, retry might help).

**New Edge Function `list-banks`:** thin read-only proxy for the bank picker UI — routed through the provider interface rather than hardcoded, since Flutterwave is the actual source of truth for which `bank_code` values the other two functions will accept.

**`packages/payments/flutterwave.ts` — rewritten, not patched:**

- OAuth2 `client_credentials` token exchange (`idp.flutterwave.com`), cached at module scope, refreshed a minute before the documented 10-minute expiry.
- `flwFetch` helper with retry (network errors and 502/504/503 only, never 4xx) — the production host was observed to be genuinely flaky during this session's own testing (intermittent 503s, `ECONNRESET`, connect timeouts, recovering on retry every time); baked the retry in rather than treating it as one-off bad luck.

- **`initiateCollection` — real, confirmed live, redesigned mid-session after the first design turned out wrong in practice.** Original plan (per the docs read first): Customer → PaymentMethod (`type: 'bank_transfer'`) → Charge. **Live-tested and rejected**: Flutterwave's real API doesn't accept `'bank_transfer'` as a payment-method type (`400 Invalid value 'bank_transfer' for PaymentMethodIn`); `'bank_account'` is accepted but returns an empty `bank_account` object — no usable virtual account number, under any field combination tried. Found instead, by testing directly: **`POST /virtual-accounts`** with `account_type: 'dynamic'` does the whole job in one call — a real account number, immediately, and (contrary to what the docs for this specific endpoint say) does **not** require BVN/NIN for a dynamic (one-off) account, only for a reusable `static` one. - **A second real bug, caught by the first live test run, not by reading code:** the original design created the Flutterwave Customer _inside_ `initiateCollection`, in the same try/catch as the rest of the flow. When the payment-method step failed (the bug above), the customer had _already_ been created at Flutterwave but its id was never persisted to `users.provider_customer_id` — so the retry tried to create a second customer with the same stable synthetic email and got a real `409 CUSTOMER_ALREADY_EXISTS`, with no way to recover the first id (v4 has no get-customer-by-email lookup). Fixed by splitting customer resolution into its own `PaymentProvider.resolveCustomerId()` method that the Edge Function calls and persists **before** ever attempting a collection — removes the failure mode instead of working around its symptom. `CollectionRequest` now takes a required `providerCustomerId`, not an email/phone the adapter resolves internally.
- **`verifyWebhook` — a real, confirmed bug fixed, not just refactored.** The previous version used `.digest('hex')`. Flutterwave's own webhook-docs verification code sample uses `.digest('base64')` — hex would have rejected every single real webhook Flutterwave ever sent. Caught by reading that sample directly this session, not assumed to still match a v3-era convention. Existing test's `sign()` helper updated to match.
- **Webhook event names corrected:** `transfer.completed`/`transfer.failed` (the session-2 guess, never confirmed against real v4 docs) were wrong. The real names, per developer.flutterwave.com's own API-overview reference, are **`transfer.disburse`** and **`transfer.reversal`**. `webhook-flutterwave/index.ts` and its test updated. Also added a `data.status === 'succeeded'` check on `charge.completed` — that event fires for every terminal charge state (succeeded/failed/voided), not just success, per the charges endpoint's own documented status enum; a non-succeeded `charge.completed` now marks the topup `failed` directly instead of being silently treated as a confirmation.

### Two real auth bugs found the moment the user actually tried logging in — neither would have been caught by code review alone

The user installed the preview build and got "unsupported phone provider" entering their number. Two separate, real problems, both found by using the real app on a real phone rather than by reading the auth screens:

1. **Phone auth was never actually turned on for this Supabase project.** `external_phone_enabled` was `false`, and `sms_provider` was set to `twilio` with every Twilio credential field `null` — so even if enabled, no real SMS could ever have sent. Nobody had caught this before because every previous session's testing created users via the Admin API with `phone_confirm: true`, which never exercises the real `signInWithOtp` path at all. Fixed for now via Supabase's built-in test-OTP mechanism (`sms_test_otp` config, set via the Management API) mapped to the user's own number with a fixed code — unblocks testing today with zero real SMS provider needed, but this only ever works for that one hardcoded number. **A real SMS provider (Twilio, matching the project's existing `sms_provider` selection, or MessageBird/Vonage/TextLocal) still needs to be provisioned before any other real user can ever receive an OTP** — flagged in "Immediate next step."
2. **The phone-entry screen never normalized the number to E.164.** The user typed the everyday local format (`0902...`); Supabase's phone auth requires `+234902...` and rejects anything else. Nothing in `(auth)/index.tsx` converted it — the placeholder text (`+234 800 000 0000`) hinted at the right format but didn't enforce it. Fixed with a small `apps/mobile/lib/phone.ts` helper (`toE164NigerianPhone`, deliberately Nigeria-only, not a full libphonenumber integration — matches this NGN-only app's "stay lite" posture) used both when calling `signInWithOtp` and when storing the pending phone for the verify screen's later `verifyOtp` call. **Needs a new EAS build to reach the user's phone** — the already-installed APK doesn't have this fix; told the user to type the `+234...` form directly as an immediate workaround on the existing install.

### Bugs this test suite caught in itself before it caught anything in the functions

Worth recording because they're exactly the kind of test-infrastructure mistake that quietly invalidates a test suite's results if not caught:

1. **Cross-user cleanup ordering.** A thread's messages can have `sender_id` pointing at _either_ participant, so tearing down "everything belonging to user X" one user at a time left the other participant's messages dangling and blocked the thread delete with an FK violation. Fixed by adding a `deleteTestThread` helper that tears down a thread as a unit, by thread id, before either participant is deleted.
2. **Platform wallet cleanup drift.** `resetPlatformWallets` zeroed `wallets.balance` directly without deleting the corresponding `ledger_entries` — exactly the bug class `fn_run_reconciliation_check` exists to catch — which leaked a stale mismatch into whichever test ran next. ### Two real bugs found and fixed during this build (not hypothetical — both would have shipped broken otherwise)

1. **`make_interval(hours => v_refund_hours)` failed at runtime** — `pricing_config.value` is `bigint`, `make_interval` wants `integer`, and Postgres won't implicitly narrow in a named-argument function call. Fixed with an explicit cast. Caught by actually calling the function, not by the migration applying cleanly (DDL applies fine; the bug only shows up when the function body executes).
2. **Earnings never actually became withdrawable.** The original function only credited `earnings_pending` at escrow release and stopped there — nothing converted it to `withdrawable_cash`, contradicting docs/03-ECONOMY-LEDGER.md §6's "automatically and immediately on release." Fixed by adding the conversion as two more ledger legs in the same release transaction (debit `earnings_pending`, credit `withdrawable_cash`, both reason `earnings_conversion` — which is exactly why that reason already existed in the item-1 CHECK constraint enum).

### One schema correction made mid-session (forward migration, nothing hand-edited)

The item-1 schema had a single `platform_revenue` wallet kind, but top-up fees are cash (kobo) and earnings-take fees are credits — two different units that can't share one balance without silently mixing them. Split into `platform_revenue_topup_fees` and `platform_revenue_earnings_cut` via a new migration (`20260912072739_extend_schema_for_functions.sql`), which also added the `withdrawal_refund_failed` ledger reason needed for `fn_fail_withdrawal`.

### One workflow mistake worth remembering for next time

Pre-created all four migration files via `supabase migration new` before writing their content, then ran `supabase db push` — which applied the still-empty files and marked them "applied" in the remote's migration history. Editing them afterward meant `db push` would silently skip the real content on the next run (matches by filename/timestamp, not content). Fixed by deleting the stale rows from `supabase_migrations.schema_migrations` and re-pushing, but the correct sequence is: **write a migration's full content before pushing it, not batch-create-then-fill.**

### A schema behavior worth knowing, not a bug

`threads.participant_a/b` reference `users(id)` **without** `ON DELETE CASCADE` (unlike `wallets`, which does cascade from `users`). This means a user with any thread history can't be hard-deleted — consistent with `ledger_entries` already being permanently undeletable once it exists. For a money-moving app this is probably the right default (can't erase transaction/conversation history via account deletion), but it means "delete a user" will need to become "suspend/anonymize a user" as a product decision later, not literal `DELETE FROM users`.

## Key decisions on record (deviations from the original verbal brief — don't "fix" these back without re-reading why)

1. **Stack:** React Native (Expo) + Supabase (Postgres/Auth/Realtime) + Flutterwave-first with Paystack provisioned behind a `PaymentProvider` interface. User-selected from options presented; see conversation history if the reasoning matters later.
2. **Message pricing is tiered**, not flat: `2 × ceil(words / 50)` credits with a 500-word hard cap — the literal brief's flat "+2 credits over 50 words, no cap" is exploitable (see `docs/06-SECURITY-FRAUD-LOOPHOLES.md` §1). Matches the brief exactly at the two points it specified (≤50 words, just-over-50). **Now implemented and verified** in `fn_send_message`.
3. **Escrow mechanic added, not in the original brief:** credits charged to the payer are held until the payee actually replies, auto-refunded if unanswered after 48h. Closes a fairness gap (payer charged into a void) the literal brief didn't address. **Now implemented** (`fn_send_message` + `escrows` table); `fn_refund_expired_escrows` exists but isn't cron-scheduled yet (item 5).
4. **Earnings auto-convert to cash immediately** on escrow release (fixed ₦10/credit rate) rather than requiring a manual "convert" step with a floating rate — simplification, see `docs/03-ECONOMY-LEDGER.md` §6 for why. **Now implemented and verified** in `fn_release_escrow`.
5. **Web target de-scoped.** Expo's template defaults to web + static SSR export; that crashed under Node SSR (AsyncStorage touches `window`) and was never actually a v1 goal (WhatsApp-shaped app is mobile-first). Switched to `single` (client-only) output. See PR #1.
6. **2% top-up fee likely doesn't cover the payment gateway's own processing fee** — flagged as an unresolved business-model question in `docs/03-ECONOMY-LEDGER.md` §3, not something the code can fix. Needs a real decision before launch (subsidize it, raise it, or floor top-up amounts).
7. **The `escrow_hold` ledger reason (from item 1) is deliberately unused.** A separate clearing-account ledger leg at hold time would need its own wallet abstraction; the `escrows` table itself already records what's held, and the per-wallet reconciliation invariant CLAUDE.md cares about doesn't require it. Documented in the functions migration's header comment.
8. **`wallet_float_kobo` dust-carry mechanic (docs/03 §3) is not implemented.** Top-up rounding remainders (sub-10-kobo) are currently just not credited anywhere — a real, small, deliberately-deferred gap, not silently dropped.
